## 目的

99 枚のプロジェクトカードと衛星カード 40 面（実効は 25 種）の効果を、共通の**フック**（効果が働く時点のイベントと修正の問い合わせ）と少数の**部品**（効果の最小単位）の組み合わせで実装する方式を決め、全カードを部品に割り当てる。実装者がこの仕様書と 002・007 だけで、効果を難度の低い順に実装できるようにする。

007 が「いつ・どの順で・誰の選択を待って解決するか」を定め、009 が「どの状態が窓を開くか」を定めた。本書は、その窓の中身である「効果そのものをどう表し、どう解決し、どう問いにするか」を定める。

## スコープ

- 対象: 効果の部品の一覧と入力・選択・既定動作、フック（トリガー時点のイベントと修正の問い合わせ）の一覧と 007 の窓との対応、条件の部品、効果の登録方式（データ駆動）と PHP のクラス構成、全 124 種の効果（プロジェクト 99 + 衛星 MOON 5 + 色別プラン 20）の部品への割り当て、実装の順序と PR の分け方、窓の「問い」の組み立て（009 の状態 31 の args の形）と衝突する効果の順序の選択（007 §6）、単体テストの方針、zombie の既定。
- 対象外: 状態遷移・状態クラス（→ 009）、効果の処理順・同時処理の規則そのもの（→ 007。本書は 007 を実装の形にするだけで、規則を変えない）、DB スキーマ・通知の詳細（→ 010。本書は必要な永続データの項目だけを申し送る）、画面（→ 012）、カード文面・FAQ の解釈（→ 002・007）。コードは書かない（擬似コードは設計の説明用）。
- 007・009・002 で決まっていない解釈は推測で確定させず、「未確定事項」に挙げる。

## 仕様

### 0. 記法と根拠

- 根拠の `002 §N` `007 §N` `009 §N` `004 §N` は各仕様書の節、`FAQ 行 N` は `faq.xlsx` の `faq` シートの行（002 §11 に転記済み）、`Q-NN` は [rule-questions.md](../development/rule-questions.md)、`未確定 N` は本書末尾の未確定事項の No.。`007 未確定 N`・`009 未確定 N` は各書の表を指す。
- 印: 【確定】= 承認済み仕様書・作者回答・FAQ で決まっていること。【導出】= それらから論理的に導かれること（新しい裁定を含まない）。【提案】= 本書の設計案（実装方式の選択で、ルールの裁定ではない）。【暫定】= 材料が足りず仮置きしていること（未確定事項に対応する番号を付ける）。
- 用語は [CLAUDE.md](../../CLAUDE.md) と 002 §3 の識別子に従う。007 の窓の記号（`PL1`〜`O4`、`AN`、`XD`）をそのまま使う。
- 007 §10 の付表（カードごとの窓・選択・資源）は**正**とする。本書の割り当て表（§7）は、これを部品の言葉に写したもので、食い違いがあれば 007 が優先する。

### 1. 設計の全体像【提案】

効果の実装を次の 5 層に分ける。

| 層 | 役割 | 置き場所（004 §3） |
| --- | --- | --- |
| 1. 効果の定義（データ） | 「どのカードの、どのフックで、どの部品を、どのパラメータで」を表す不変のデータ `EffectSpec` | `Material/` |
| 2. 部品（ハンドラ） | 部品 1 種ごとに、条件の判定・問いの生成・検証・適用を持つクラス | `Effects/Parts/` |
| 3. エンジン | プールの収集、稼働条件の再確認、衝突の判定、順序の決定、解決ループ、使用済みの管理。部品の種類を知らない | `Effects/` |
| 4. 修正の問い合わせ | コスト・対象区域・枚数・禁止などを、修正部品を集めて畳み込んで返す | `Effects/Query/` |
| 5. ゲーム状態との接点 | 読み取り用の `GameView` と、書き込み用の `GameMutator`（インターフェース）。実装は `Data/`・`Flow/` 側 | `Effects/Context/`（インターフェースのみ） |

- 【提案】`Effects/` は BGA のクラス（`Table`、`GameState`）を継承せず、フレームワークを直接呼ばない（004 §5.1・§6.1）。DB・乱数・通知は `GameView` / `GameMutator` / 注入された乱数源を通して使う。これで PHPUnit だけで全部品を検査できる（004 §10）。`pe` 接頭辞はフレームワークを継承するクラス向けの規則なので、`Effects/` のクラスには適用しない（004 §6.2）。
- 【確定】状態クラス（009 の 30・31・32、ドライバ）は問いを渡して答えを受けるだけで、問いの組み立て・衝突の判定・デフォルトの順は `Effects/` が行う（009 §6.2）。
- 【確定】効果は所属カードの `name_id` で識別する（002 §3.1）。MOON 面は色が違っても同じ `name_id`。

### 2. 効果の部品

#### 2-1. 部品の種類

効果は 4 種の部品の組み合わせで表す。部品は全部で **29 種**（結果 15・修正 13・禁止 1）で、これに**支払い 3 種**と**条件 13 種**が加わる。

| 種別 | 数 | 役割 | 働く場面 |
| --- | --- | --- | --- |
| 結果部品（R） | 15 | 状態を変える（マヤ、予算、カード、燃料、衛星の位置・向き・構成、通信確立、アクションのボーナス） | 窓（フックのイベント）の解決 |
| 修正部品（M） | 13 | 数量・対象範囲・コストを変える。状態を変えない | 修正の問い合わせ（数量を決める時点） |
| 禁止部品（F） | 1 | 選択肢を取り除く（配備不可・転回不可・通信確立不可） | 選択肢を作る時点と解決時 |
| 支払い（C） | 3 | 効果を使うための代価（マヤ、マヤの段階、手札の捨て） | 結果部品の前（[Use] のとき） |
| 条件（K） | 13 | フックのイベントや問い合わせの文脈が効果の条件を満たすかを判定する | トリガーの収集時と解決の開始時 |

稼働条件 `ACTIVE_ONLY` と効果タイプ（`CONSTANT` / `ACTIVATED` / `ON_DEPLOY` / `ON_LAUNCH`）は部品ではなく `EffectSpec` の項目で、エンジンが 007 §3 のとおり評価する。

#### 2-5. 支払い（C、3 種）

効果を使う（[Use] を選ぶ）ときの代価。支払いは**解決の時点で払えるか**を判定し、足りなければ売却を促す（008 §2-6）。[Use] の答えに売却するカードを同梱できる。

| C2 | `PAY_MAYA_TIER` | 段階を選んで払う。段階ごとに結果の量が変わる | P034（2 / 3 / 4 / 5 マヤ → 1 / 2 / 3 / 4 区域）、P072（4 / 7 / 10 マヤ → 残す枚数 +1 / +2 / +3） |
| C3 | `DISCARD_COST` | 手札を捨てる（R04 と同じ処理。売却額は得ない） | P070（追加で 1 枚）、P074（1 枚）、P076（2 枚） |

#### 2-6. 条件（K、13 種）

条件は `EffectSpec.conditions` に並べ、すべて満たすときだけトリガーされる（AND）。トリガーの収集時と解決の開始時の 2 回評価する（007 §3-2。解決の途中では再評価しない）。評価に使うのは「イベントの内容」（`GameEvent`）と、問い合わせの文脈（`QueryContext`）。

### 4. 効果の登録方式【提案】

#### 4-1. 方式の比較

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A. カードごとのクラス | 124 種の効果それぞれに 1 クラス（`Card011TwinDeployTechnician` など）を作る | 原文との対応が 1 対 1 で読みやすい | 配備コスト修正 12 枚、通信確立 14 枚、ドロー 15 枚など同じ処理が重複する。窓・使用済み・稼働条件の共通処理を全クラスが呼ぶ必要があり、漏れやすい。007 §10 の付表（窓・選択・資源）と実装の一致を機械的に検査できない |
| B. 完全なデータ駆動 | 全効果を「フック・部品・パラメータ」で表し、固有の効果も共通ハンドラで解く | 重複がない。付表との一致をデータで検査できる | P022（付け替え）、P024（入れ替え）、P035（ギャンブル）のように 1 枚だけの手順は、無理に一般化すると読みにくい |
| C. データ駆動＋専用部品（採用） | 全効果を `EffectSpec`（データ）で表す。部品は共通のものと、1 枚専用のもの（R06・R10・R12・R13、M05・M07〜M09・M12・M13 の 10 種）を同じインターフェースで持つ | 共通処理はエンジン 1 か所。専用の手順は専用部品のクラス 1 つに閉じる。カード → 部品の対応が表（§7）になり、007 付表と照合できる | `EffectSpec` の項目が多い（§4-2） |

**採用: 案 C。** 理由は次のとおり。

1. 29 種の部品のうち 19 種は複数のカードが共有する（最多は R03 の 15 枚、R11 の 14 枚、M01 の 12 枚。R04 は P087 の結果としては 1 枚だが、支払い C3 として P070・P074・P076 でも使う）。重複を避ける利益が大きい（数は §7 の表から数えられる）。
2. 007 の窓・資源・選択の列は部品とフックから機械的に決まり、データで持てば付表との一致をテストで検査できる（§11）。
3. 専用部品は 10 種に収まり、案 A の「カードごとの手順」を専用部品の中に残せる。原文との対応は §7 の表で 1 カード 1 行になる。
4. 004 §6.1 の `Material/`（不変のデータ）と `Effects/`（振る舞い）の分離にそのまま合う。

#### 4-2. `EffectSpec` の項目

1 カード 1 効果（002 §3.1）なので、`EffectSpec` は 1 カードに 1 つ（支払い C と結果 R を 1 つの `EffectSpec` に持つ）。

| 項目 | 型 | 内容 | 出典 |
| --- | --- | --- | --- |

| `hook` | `Hook`（列挙） | §3 のフック | 007 §10 の窓の列 |

- 【導出】反応効果（`DEPLOYED` など）は、`selfOnly = false` のとき、そのカード自身を配備したイベントには反応しない（007 §3-2、FAQ 行 11・16）。エンジンの共通規則で、`EffectSpec` には持たない。
- 【導出】`kind = ACTIVATED` の使用済みはカード単位（007 §3-1）。使用済みは効果が実際に解決されたときに付き、[Skip]・対象なしでは付かない。`CONSTANT`・`ON_*` には使用済みがない。

- 【提案】`CardEffects::forProject(string $cardId)`（`P001`〜`P099`）と `CardEffects::forSatelliteFace(Shape $shape, Plan $plan)`（MOON 面は色を引数に取らない）の 2 つの入口を持ち、カード ID から `name_id` を引く表は `Material/CardDefinitions` が持つ（004 §6.1）。

#### 5-3. 1 人分の解決ループ【提案】

007 §6-3 の手順を、実装の形にしたもの。`advance(p)` はプレイヤー `p` について、自動で進められるところまで進め、問いが要る所で止まる。

```text
advance(p):
    loop:
        pool[p] から、再確認（稼働条件・条件・対象の有無。007 §3-2）に失敗した要素を捨てる
        if pool[p] が空: return DONE

        sets = ConflictResolver.sets(pool[p])          # 衝突する効果の集合（007 §6-2）
        if 順序が未決定の集合がある:
            return ASK(ORDER, その集合)                  # §6-4

        head = 順序が決まった集合の先頭                    # 衝突する効果は、順序が決まったものから 1 つずつ
        if head がない:
            # 衝突する効果がない。デフォルトの順（DefaultOrder）で強制の効果を自動で解決し、任意の効果の問いを並べる
            auto = pool[p] のうち 強制で選択のないものを DefaultOrder で
            if auto がある: resolve(auto の先頭); continue
            return ASK(EFFECT, pool[p] のうち任意または選択のある全部)   # 並列の問い（§6-1）

        if head が強制で選択のない効果: resolve(head); continue
        return ASK(EFFECT, [head])                       # 衝突の順序が決まったものは 1 つずつ問う

resolve(entry):
    for stage in 1..spec.stages:
        answer = (自動なら null / 問いなら受け取った答え)
        outcome = part.apply(ctx, entry, stage, answer)
        outcome.events の各イベント: collect(hook, event)        # 連鎖。同じプレイヤーのプールに加わる（007 §8-1）
    ACTIVATED なら 使用済みにする
    entry を DONE にする
```

- 【確定】衝突する効果が 1 つでもあれば、その集合の順序をプレイヤーが選び、選んだものを解決するたびにプールを再計算する。衝突しない効果は、衝突する効果がすべて解決された後に、デフォルトの順で処理する（007 §6-3）。
- 【提案】プレイヤーが [Confirm order] で並べた順は、集合全体の順として保存する（008 §5-2 の UI は 1 画面で並べ替える）。解決の途中で連鎖により新しい効果がプールに加わり、それが未解決の効果と衝突する場合だけ、残りと新しい効果で改めて順序を聞く（前回の相対順を初期の並びにする）。衝突しなければ、保存した順のまま最後まで解決する。これは 007 §6-3 の「解決するたびに再計算する」と結果が同じで、聞く回数を減らすだけの実装上の工夫。
- 【導出】[Skip] した効果は他の効果の順序に影響しない（007 §6-3）。使用済みにならず、そのトリガーは失効する（007 §3-1）。
- 【導出】強制で選択のない効果（`optional = false` かつ `buildFields` が空）は問いを出さずに自動で解決する（Q-13）。ログには出す。
- 【提案】多段の効果（P087: 引く → 捨てる）は、段ごとに `PoolEntry.stage` を永続化し、再読み込み・再接続で途中から再開できるようにする。
- 【確定】1 つの窓の効果数に上限 200 の安全弁を置く（007 §8-3、009 §3.5）。超えたら窓を強制終了し、ログに残す。

### 6. 窓の「問い」の組み立て（009 の状態 31 の args）

#### 6-1. 問いの全体の形【提案】

状態 31 の `getArgs` は、本人向けの `_private[playerId]` に次の形を入れる（009 §6.2）。公開部分には、待機中の表示用に「誰が・どのカードの効果の選択中か」だけを入れる（効果のカードは公開情報。007 §7-2、008 §5-1）。

```text
_private[playerId] = {
    windowId:   "DE" など,
    pending:    [{entryId, cardId}, ...],         # このプレイヤーのプールの残り（表示用）
    questions:  [Question, ...]                   # 今答えられる問い
}

Question (type = "ORDER") = {
    entries:      [{entryId, cardId, forced: bool}],   # 順序を選ぶ集合（強制の効果も含める。007 §6-2 の例: R010 と P006）
    defaultOrder: [entryId, ...]                        # デフォルトの順（007 §6-3）
}

Question (type = "EFFECT") = {
    entryId, cardId,
    mandatory:  bool,                             # 真なら [Skip] なし（P087 の捨てなど）
    cost:       {kind: "NONE" / "MAYA" / "MAYA_TIER" / "DISCARD", amount | tiers, canPay: bool, shortfall: int},   # 払えない場合は売却で足りるかを shortfall で示す（008 §2-6）
    fields:     [Field, ...],
    preview:    {...}                             # 結果の見込み（例: 配備コストの内訳、燃料の残り）。サーバーが計算する（008 §2-6）
}

```

- 【確定】アクション名は 009 §6.2 のとおり `actUseEffect` / `actSkipEffect` / `actOrderEffects`。答えの形は次のとおり。
  - `actUseEffect(entryId, fields, sell)`: `fields` は問いの `key` → 値。`sell` は売却するカード ID の配列（空でよい。008 §2-6 の同梱）。
  - `actSkipEffect(entryId)`: 任意の効果を使わない。`mandatory` の問いには使えない。
  - `actOrderEffects(entryIds)`: `ORDER` の集合の全要素を、解決したい順に並べた配列。
- 【導出】`questions` は次のとおり決まる（§5-3）。
  1. 順序が未決定の衝突する集合があれば `ORDER` の問い 1 つだけ（他の効果は待つ。007 §6-3 の手順 3）。
  2. 順序が決まっていれば、先頭の効果の `EFFECT` 1 つだけ。
  3. 衝突する効果がなければ、任意・選択ありの効果すべての `EFFECT`（並列。どの順で答えてもよい。008 §4「候補のカードを全部並べる」）。
- 【導出】プールが 1 要素のときは `ORDER` を出さない（007 §6-3）。
- 【確定】窓内の選択は確定したら取り消せない（007 §7-1）。ステップの本体（アクションカードの選択、打ち上げ・配備などのメイン・ボーナスの選択）は全員確定まで選び直せるが、窓の問いは別（009 §6.5）。
- 【提案】`pending` は、待機中（`ORDER` 待ち・並列の問いの回答待ち）の効果を本人に見せるための表示用で、答えられるものは `questions` に入れる。

#### 6-4. 衝突する効果の順序の選択（007 §6）の実装【提案】

**資源の記号と範囲。** 007 §6-2 の記号（`M+` `M−` `B+` `H+` `H*` `F+` `F−` `P` `D` `C` `Cr` `L` `A`）に、**範囲**を付ける。

| 範囲 | 意味 |
| --- | --- |
| `PLAYER` | プレイヤー単位の資源（マヤ、予算、手札） |
| `SAT(id)` | 特定の衛星の資源（燃料、位置、向き、構成、通信確立、稼働状態） |
| `ALL_SATS` | 自分の全ての衛星（007 §6-2 の規則 4: 衛星や対象をプレイヤーが選ぶ効果） |

- 【導出】007 §6-2 の規則 4 は、選ぶ前は「どの衛星か分からない」ので全衛星に触れるものとして扱う、という意味で、規則が衛星単位の粒度を前提にしている。「この衛星」の効果は `SAT(その衛星)`、プレイヤーが衛星を選ぶ効果（P004、P024、P038 の回復先、P044 の転回先ほか）は `ALL_SATS`、マヤ・予算・手札は `PLAYER`。
- 衝突の判定（`ConflictResolver`）は 007 §6-2 の 4 規則そのまま:
  1. 同じ記号の資源で、読み書き（`M−` `H*` `P` `D` `C` `L` `A`）の効果と、他の効果が、範囲が重なって触れる。
  2. 異種の加算（`F+` と `F−`）が、範囲が重なって触れる。
  3. `Cr`（読み）と `C`（書き）が、範囲が重なって触れる。
  4. 選ぶ効果は `ALL_SATS`（任意の `SAT(id)` と重なる）。
  - 同じ種類の加算同士（`M+` と `M+`、`H+` と `H+`、`B+` と `B+`、`F+` と `F+`）は衝突しない。
- 衝突が連なる効果を 1 つの集合にまとめる（連結成分）。集合ごとに 1 つの `ORDER` の問いを出す。集合が複数あれば、それぞれ別の問い（`questions` に複数入れてよい）。
- `touches` は `EffectSpec` に持ち、既定は部品から導く（各部品が `defaultTouches(params)` を返す）。**007 §10 の付表の「資源」列と完全に一致すること**を単体テストで検査する（§11）。一致しない場合は 007 を正として、本書か実装を直す。
- デフォルトの順（`DefaultOrder`）: 衛星の順は衛星カードの形状順（HAMMER、RETRO、SCALLOP、CONCORDE、STEALTH）、1 つの衛星の中では衛星カード → 一番早く配備したカードから上へ、衛星に属さない効果は最後（007 §6-3）。[Confirm order] の初期の並びと、zombie の答えはこの順。
- 007 §6-2 の例の再現: P006（`M−` `B+`）と R010（`M+`）は `M−` と `M+` で衝突 → 順序を聞く。P011（`H*`）と P023（`H+`）は衝突 → 聞く。P013（`B+`）と P023（`H+`）は衝突しない → 自動でデフォルトの順。

#### 6-5. 企画（V）の選択効果（009 未確定 6）【提案】

009 の暫定案どおり、`PROPOSAL_OPTIONS` の効果（P068、P070、P072）は 91 `ProposalKeepChoose` の問いに含め、窓を開かない。`ProposalQuery` が次を返す。

#### 6-6. セットアップ手順 16 の配備フェイズ【確定】

全衛星が非稼働のため、`ACTIVE_ONLY` の効果は働かず、稼働コスト +5 は不要（007 §7-4）。`DEPLOYED` の窓は 009 のとおり 60 のメイン・ボーナスの後に開く。`BONUS_DECLARE`（XD）はセットアップでは開かない（009 §3.7）。窓内の選択（P011 の追加配備、P022 の付け替え、P024 の入れ替え）は全員同時に行う。

### 7. 全カードの割り当て表

#### 7-1. 凡例

- **カード**: ID と名前（002 §5・§6）。1 行が 1 種の効果（MOON 面は色違い 4 枚で 1 行）。合計 99 + 5 + 20 = 124 行。
- **フック**: §3 のフック。窓の記号との対応は §3-1・§3-2。
- **種**: 効果タイプ。常 = `CONSTANT`、起 = `ACTIVATED`、配 = `ON_DEPLOY`、打 = `ON_LAUNCH`（002 §3.4）。
- **稼**: 稼働条件。◎ = `ACTIVE_ONLY`、— = `ANY`（002 §3.5）。
- **部品**: §2 の部品 ID と名前。支払いは `C1(2)` のように括弧にマヤの額を書く。
- **パラメータ・条件**: 部品のパラメータと、`EffectSpec.conditions`（K01〜K13）。K01 の `THIS` / `OTHER` / `ANY` は `EVENT_SATELLITE` の範囲（このカードのある衛星 / 自分の他の衛星 / 自分のどれか）。
- **選**: 007 §10 の付表と同じ記号。自 = 強制で自動、任 = 任意（[Use] / [Skip]）、対 = 対象・数値・カードの選択（フィールド。括弧に型）、— = 選択なし（修正・禁止）。
- **難**: 実装の難度（7-2）。
- 007 §10 の「窓」「選択」「資源」の列と矛盾しないことを、§11 のテストで検査する。

#### 7-2. 難度の目安

| 難度 | 内容 |
| --- | --- |
| ★1 | 強制で自動、選択なし、1 段で完結。パラメータだけで決まる（固定量のマヤ・予算・ドロー、固定の修正、禁止） |

### 10. zombie 時の効果ごとの既定

方針は 009 §9.1 のとおり「ゲームを止めず、失敗リスク（コストの支払い、不利な構成変更）を取らない」。ランダムは使わない。状態 31 の `zombie(playerId)` は、`EffectEngine::zombie()` を呼び、プールが空になるまで次を繰り返す。

| 場面 | 既定 |
| --- | --- |
| 強制で選択のない効果（R01〜R03、R05、R10、R15 ほか） | 通常どおり自動で解決する（zombie でもマヤ・予算・カードは得る） |
| 任意の効果（`optional`） | [Skip]。使用済みにならない |
| `ORDER` の問い | デフォルトの順（007 §6-3）を確定する |
| 起動の修正（`USE_MODS`） | 使わない（空の配列）。ステップ本体は 009 §9.2 のとおり [Pass] |
| 売却 | 自動の売却はしない（008 §2-6） |
| 支払い | 払えるかどうかにかかわらず、任意の効果は [Skip] のため支払わない |
| R04 の強制の捨て（P087 のみ） | 直前に引いたカードを捨てる（手札が増減しない）。引けなかった場合は手札のカード ID 昇順で最初のカード。手札が空なら何もしない（未確定 3） |
| R12（P022 の付け替え） | 現在の配置のまま（変更なし） |
| 企画のオプション（M07、M08、P070） | 辞退（009 §9.2 のとおり引いた順の先頭から必要な枚数を残す） |
| 部品別の対応 | R06・R07・R08・R09・R11・R13・R14 は辞退（`defaultAnswer` が null） |

- 【導出】辞退のない強制の問い（`mandatory`）は P087 の捨てだけ。他のすべての問いは [Skip] か「変更なし」で答えられる。
- zombie でもゲームを早期終了させない（009 §9.1）。zombie の強制の効果（P003 の +2 マヤなど）は通常どおり働く。
